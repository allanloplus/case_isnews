03

個案背景：為什麼是 PHP？

理解「底層元件」漏洞為何比單一系統漏洞更可怕

🧱 網站的共同地基

PHP 是伺服器端程式語言，依 W3Techs 統計，在可辨識後端語言的網站中約占 七成。WordPress、Drupal、Joomla、許多電商與形象網站，以及不少設備的 Web 管理介面都建立在 PHP 上。

🕰 十多年的技術債

研究者指出，問題程式碼最早可追溯至 PHP 5.4，「過去十年發布的幾乎每個版本」都受至少一項漏洞影響。同時約有三成以上網站仍在跑官方已不支援（EOL）的版本。

🤖 AI 改變了遊戲規則

過去這類深藏在記憶體管理中的瑕疵，需要頂尖研究員長時間投入。這次是研究員借助 AI 模型閱讀、推理 PHP 原始碼後找到，並快速驗證可在 WordPress、Drupal 等系統上做到免登入接管。

🍔 用「漢堡」理解影響層次

層次例子這次有沒有事？只更新這層夠嗎？
應用程式／外掛WordPress、佈景主題、外掛、自寫程式不是漏洞所在，但會被當成入口不夠
語言執行環境PHP 引擎（mod_php、PHP-FPM、php-cgi、FrankenPHP、LiteSpeed）漏洞所在必須更新
Web 伺服器Apache、Nginx、LiteSpeed作為承載 PHP 的通道依架構
作業系統／容器映像Linux 發行版套件、Docker imagePHP 常隨 OS 套件或映像一起出貨需重建映像
邊界防護WAF、CDN（Cloudflare、Akamai 等）可提供虛擬修補，爭取時間只是補償控制

🎯 受影響範圍

  • 所有處理網頁請求的 PHP 部署：Apache + mod_php、PHP-FPM、php-cgi、FrankenPHP、LiteSpeed
  • 研究者實證：wordpress:latest、drupal:latest、joomla:latest 皆可免登入 RCE
  • 回溯至 PHP 5.4 的多個版本

🩹 修補與緩解

  • 唯一完整解法：更新 PHP（8.5.12／8.4.27／8.3.36／8.2.35）
  • 8.1 以下：官方僅提供原始碼修補，需自行編譯，或規劃升級
  • WAF／CDN 虛擬修補：爭取時間，不能取代更新
  • 調整記憶體與上傳大小限制：官方表示無法完全阻止攻擊

🔍 修補後別忘了

  • 檢查 Web 目錄是否有不明檔案（Webshell／後門）
  • 檢查異常排程（cron）、新增帳號
  • 因有記憶體外洩風險：輪替資料庫密碼、API 金鑰、Session 密鑰、憑證
  • 重建容器映像，而不只是更新執行中的容器

各國與企業因應

「先關站」vs.「帶傷運轉」——不同組織的風險決策

🇯🇵 日本：首相親自喊話，企業大量「預防性關站」

  • 首相高市早苗於 X 發文：「今晚就請處理」，並指暫停網站是有效降低風險的方式之一
  • ANA、JAL 暫時關閉企業官網；JR 西日本關閉約 60 個集團網站
  • 三菱 UFJ 銀行暫停部分線上服務；靜岡銀行、77 銀行部分受影響
  • SEGA、pixiv、niconico、BASE、櫻花網路等暫停全部或部分服務；財務省暫停部分網頁
  • 網路報導連演員阿部寬著名的「極簡官網」也罕見進入維護（單一來源報導）

🇪🇺 歐洲：政府帶頭暫停公共服務

  • 荷蘭 NCSC 暫停部分服務，鹿特丹港、政府入口網、部分醫院網站受影響
  • 芬蘭 Valtori 預防性下線政府對外網站；丹麥 Kombit 關閉多項服務（含全國學校溝通平台）
  • 法國內政部所有網站進入預防性維護模式
  • CERT-EU：無法立即修補者，建議將對外網站下線；英國 NCSC：允許修補前先下線
  • 維基百科部分系統、Internet Archive 短暫離線

🇺🇸 美國：情資與雲端業者動員

  • 白宮表示 10/17 即已得知並協調聯邦機關；FBI、NSA 發布聲明呼籲更新
  • AWS：揭露前已在蜜罐觀察到攻擊，揭露後出現廣泛利用
  • Cloudflare、Akamai、Fastly、Google Cloud、Vercel 等陸續推出 WAF 規則
  • OpenAI 召集維護者、研究者、資安業者與政府組成協調聯盟

🇹🇼 台灣：資安署五步驟建議

  1. 盤點所有 PHP 系統與套件
  2. 確認版本，依官方公告完成更新
  3. 檢視日誌與異常存取；有可疑跡象時檢查相關帳號與憑證
  4. 無法立即更新者，以 WAF 阻擋攻擊
  5. 前兩者皆不可行時，才考慮暫停服務

可向 TWCERT/CC 尋求協助。

Allan 顧問觀點：注意台灣資安署的順序是「修補 → WAF → 才關站」，而日本許多企業是「先關站 → 再修補」。兩者沒有絕對對錯，差別在於組織是否事前就定義好「誰有權在什麼條件下關站」。能在一小時內做出關站決策的企業，通常早就把它寫進營運持續計畫（BCP）與緊急變更程序裡了。

AI：資安的雙面刃

同一把刀，防守方拿來找漏洞，攻擊方拿來寫攻擊程式

🛡 防守方的 AI

  • 閱讀龐大原始碼，找出人類十多年沒發現的瑕疵
  • 協助撰寫概念驗證、偵測規則、驗證修補是否有效
  • 開源專案定期自動掃描（AI 業者推出免費掃描計畫）
  • Google DeepMind：前沿 AI 是網路防禦的「遊戲規則改變者」
AI

⚔️ 攻擊方的 AI

  • 拿到修補程式差異（patch diff），用 AI 快速反推攻擊方式
  • 大規模、自動化掃描全球曝險主機
  • 把「理解弱點」到「可用的攻擊程式」的時間大幅縮短
  • OpenAI：同樣能力「也能幫攻擊者快速開發攻擊工具」

🔄 漏洞「通膨」

AI 讓漏洞發現量上升，企業將面對更多、更頻繁的緊急修補。修補能力（人力、流程、測試環境）會成為新的瓶頸。

⏩ 揭露時程更難保密

多方各自用 AI 發現同一漏洞、協調揭露的參與者變多，消息外洩、時程被迫提前的機率上升。

🧭 治理必須跟上

企業若要在自身開發或測試導入 AI，需同時規範授權範圍、資料保護與結果驗證（可參考 ISO/IEC 42001 AI 管理系統）。

09

個案重點整理

八個帶得走的觀念

底層元件漏洞＝供應鏈風險

漏洞不在你寫的程式，而在你「依賴」的語言執行環境。資產清冊必須盤到元件與版本層級（SBOM）。

免登入 RCE 是最高優先等級

CVSS 9.2、無需驗證、可遠端利用、且有公開關注，符合「立即處理」條件，不應排入一般維護窗口。

EOL 版本是定時炸彈

8.1 以下只有原始碼修補。長期不升級的系統，在緊急時刻將面臨「無法修補」的窘境。

攻擊可能早於公告

本案攻擊比正式揭露早約四天。威脅情資與異常偵測，是「修補之前」唯一的防線。

補償控制要預先準備

WAF／CDN 虛擬修補、網段隔離、暫停服務等手段，需事先建置與演練，才能在數小時內啟用。

關站是合理的風險決策

關站換取時間，本質是「可用性 vs. 機密性／完整性」的取捨，需要事前授權與明確觸發條件。

修補≠結案

有記憶體外洩風險時，需輪替金鑰與憑證、檢查後門，並保存證據以利後續鑑識與法遵通報。

AI 加速攻防兩端

漏洞發現與利用的速度同時提升，「從公開到被攻擊」縮短至小時級，漏洞管理 KPI 與流程需要重新設計。

阿拉蕾：管理面要問的是「制度有沒有準備好」——資產、風險、決策權責與技術債。

Allan Lo 顧問
常見的盲點
  • 資產清冊只盤到「主機」或「系統名稱」，沒有盤到軟體元件與版本。
  • 行銷活動網站、委外建置的官網、子公司網站、舊專案測試機屬於影子 IT，不在 IT 管轄內。
  • NAS、防火牆、印表機、IoT 設備的 Web 管理介面也可能內含 PHP，卻被歸類為「設備」。
  • 雲端 SaaS／虛擬主機的責任歸屬不清，以為「主機商會處理」。
建議作法
  1. 資產清冊延伸至元件層級，對自建與委外系統要求提供 SBOM，並與弱點掃描結果串接。A.5.9A.8.8
  2. 導入外部攻擊面管理（EASM）：定期從外部掃描公司網域、IP 段，找出未登錄的對外服務。
  3. 每筆資產都有明確的擁有者（Owner）與技術聯絡窗口，含委外廠商的緊急聯絡方式。A.5.9
  4. 委外合約與供應商清單中標註「使用之主要技術元件」。A.5.21
💡 衡量指標：「從重大漏洞公告到完成受影響資產清單」所需時間（Mean Time to Inventory）。成熟組織應能在 1–4 小時內完成。

M3約三成以上網站仍執行官方不再支援的 PHP 版本。企業該如何治理「技術債」與 EOL 軟體？關鍵字：生命週期管理、風險登錄、預算規劃顧問參考答案收合
Allan Lo 顧問
為什麼 EOL 系統特別危險

本案中 PHP 8.1 以下僅提供原始碼修補，需自行編譯；許多委外系統或老舊系統根本找不到人處理。平時「還能跑」的系統，在緊急時刻會變成「無法修補」的系統。

治理建議
  1. 訂定技術生命週期政策：主要元件（OS、語言、資料庫、框架）在 EOL 前 6–12 個月須完成升級規劃。A.8.8A.8.32
  2. 無法升級者列入風險登錄表，由資產擁有者正式簽署風險接受，並訂定補償控制與到期日。（ISO 27001 第 6.1.3 節風險處理）
  3. 將升級成本納入年度預算與系統開發合約，例如要求委外廠商提供版本升級維護服務。A.5.20
  4. 每季向管理審查會議報告 EOL 資產數量與趨勢。（第 9.3 節管理審查）
💡 給管理階層的一句話：技術債就像信用卡循環利息，平時看不出來，出事時一次結清，而且利率很高。

Allan Lo 顧問
可觀察的訊號（依研究者建議整理）
  • 異常的 multipart 上傳請求，之後緊接著 memory limit 錯誤或大量 HTTP 500。
  • 回應中出現異常巨大或格式錯誤的 PHPSESSID cookie（記憶體外洩的跡象）。
  • PHP-FPM worker 不明原因頻繁重啟、崩潰（segfault）紀錄。
  • Web 行程帳號（如 www-data）產生子行程、對外連線、寫入 Web 目錄。
需要哪些日誌？
  • Web 伺服器存取／錯誤日誌、PHP-FPM 日誌、系統日誌（含 segfault）。A.8.15
  • WAF／CDN 日誌（看是否有規則命中）。
  • 端點偵測（EDR）或主機層行程監控。A.8.16
  • 對外連線的網路流量紀錄。
💡 實務建議：回溯檢查期間至少涵蓋正式揭露前 1–2 週（本案攻擊早於公告約四天）。另外，日誌必須集中保存在 Web 主機以外的地方，否則主機失守時日誌也可能被竄改。

不行！更新只是「把門關上」，但要確認小偷是不是已經在屋子裡。

修補後檢查清單
  1. 確認更新生效：檢查實際執行中的 PHP 版本（不只是套件版本），重啟所有 PHP-FPM／Web 服務。
  2. 容器環境：重建映像並重新部署，而非只在執行中的容器內更新。
  3. 後門檢查：Web 目錄內不明 PHP 檔、最近修改的檔案、異常排程、新增帳號、SSH 金鑰。
  4. 機敏資訊輪替：由於漏洞可外洩行程記憶體，資料庫密碼、API Key、Session 加密金鑰、TLS 私鑰等應評估輪替。A.8.24
  5. 證據保存：若發現入侵跡象，先保全日誌與映像，再進行清除，以利鑑識與法遵通報。A.5.28
  6. 經驗學習：召開事後檢討，更新程序與演練劇本。A.5.27

L1若公司網站因未及時更新 PHP 而遭入侵、導致會員個資外洩，公司可以主張「漏洞是 PHP 的問題」而免責嗎？關鍵字：個資法第 27 條、第 29 條、適當安全維護措施顧問參考答案收合
Allan Lo 顧問
原則上很難免責
  • 個資法第 27 條：非公務機關保有個資檔案者，應採行適當之安全措施。在官方已釋出修補、主管機關公開呼籲的情況下仍長期未處理，很難主張已盡適當安全維護義務。
  • 個資法第 29 條：非公務機關違反規定致當事人權益受損，應負損害賠償責任，但能證明無故意或過失者不在此限——舉證責任在企業端。
  • 個資法第 48 條：未採行適當安全措施，主管機關可處罰鍰並令限期改正；情節重大者罰鍰更高。
  • 第 12 條：個資被竊取、洩漏時，應查明後以適當方式通知當事人。
企業能做的「舉證準備」
  • 保存漏洞情資收到時間、評估紀錄、修補或補償控制的執行時間。
  • 保存決策紀錄（例如為何選擇 WAF 而非關站）。
  • 平時的弱點掃描、修補 SLA 達成率報表。
💡 顧問提醒：「我們有在做」和「我們能證明有在做」是兩回事。ISMS 的紀錄，就是法律上的舉證素材。
L2若確認遭入侵，企業有哪些通報義務與時限？上市櫃公司、受資安法規範者、有歐盟客戶者分別要注意什麼？關鍵字：資通安全管理法、重大訊息、GDPR、NIS2顧問參考答案收合
Allan Lo 顧問
適用對象主要規範重點時限／義務
公務機關、特定非公務機關（關鍵基礎設施提供者等）資通安全管理法及資通安全事件通報及應變辦法知悉資安事件後 1 小時內通報；依事件等級於期限內完成損害控制或復原（第 1、2 級 72 小時；第 3、4 級 36 小時）
上市、上櫃公司證交所／櫃買中心重大訊息規範、上市上櫃公司資通安全管控指引發生重大資安事件，應依規定發布重大訊息並說明影響與因應
保有個資之企業個人資料保護法、各目的事業主管機關之個資安全維護辦法通知當事人；部分產業須於規定期限內通報主管機關

💡 實務建議：事件應變程序中應預先整理「通報對象、時限、窗口、範本」一覽表，避免事件發生時才開始查法條。A.5.24A.5.31
L3網站由委外廠商開發、架設在虛擬主機或雲端上。若因廠商未更新 PHP 而出事，責任如何分配？合約該怎麼寫？關鍵字：委外管理、共同責任模型、合約條款顧問參考答案收合
Allan Lo 顧問
先釐清：責任可以委外，當責不能委外

對當事人與主管機關而言，企業仍是個資的蒐集者與保有者，必須對受託者盡監督義務（個資法施行細則亦要求委託機關對受託者為適當監督）。廠商的過失，企業通常只能事後依合約求償。

共同責任模型要說清楚
  • IaaS／VM：OS 與 PHP 更新通常是客戶責任。
  • 共享虛擬主機／PaaS：多半由業者負責 PHP 版本，但需確認是否允許客戶自選舊版。
  • 委外開發維運：依合約約定，未約定時常陷入「互相以為對方會處理」。
建議合約條款
  1. 重大漏洞（如 CVSS ≥ 9 或主管機關警示）之修補時限，例如 24–72 小時內修補或提出補償控制。
  2. 廠商知悉資安事件之通報時限與窗口。
  3. 維護期間內的元件版本升級義務與費用約定，避免 EOL。
  4. 稽核權與配合鑑識義務、日誌保存期限。
  5. 違約責任、損害賠償上限與資安保險要求。

L4員工聽說 AI 可以找漏洞，就拿 AI 工具去掃描合作廠商或競爭對手的網站「看看有沒有中」。這樣有法律風險嗎？關鍵字：妨害電腦使用罪、授權測試、負責任揭露顧問參考答案收合
Allan Lo 顧問
有，而且風險不小
  • 刑法第 36 章妨害電腦使用罪（第 358 條起）規範無故入侵他人電腦、無故取得或變更電磁紀錄、干擾電腦系統等行為。未經授權發送攻擊請求驗證漏洞，可能構成相關罪責。
  • 即使出於好意，未經授權的掃描也可能觸發對方事件應變、造成服務中斷，衍生民事求償。
  • 員工以公司設備、公司名義為之，公司亦可能面臨商譽與法律風險。
正確作法
  • 只測試自有系統或取得書面授權（明確範圍、時間、方法）的系統。
  • 發現他人系統漏洞時，循負責任揭露管道通報（如對方漏洞通報窗口、TWCERT/CC），參考 ISO/IEC 29147。
  • 公司政策明訂 AI 工具與資安測試工具的使用規範。A.5.10A.6.2

溝通原則
  • 主動、簡潔、不恐慌：說明「為了預防性的資安維護」，而不是「我們被駭了」（若尚無入侵證據）。
  • 提供替代管道：客服電話、實體門市、App 等，降低對客戶的影響。
  • 給出預期時間：即使只是「預計 X 時前更新進度」。
  • 口徑一致：客服、公關、業務使用同一份 Q&A。
本案觀察

日本大型企業普遍以「系統維護」公告暫停服務，在首相公開呼籲的社會氛圍下，預防性關站反而被視為負責任的表現，商譽衝擊相對有限。這說明社會情境會影響溝通策略的成效。

E4中小企業沒有專職資安人員、官網也只是委外架設的 WordPress，面對這類事件該怎麼辦？關鍵字：資源有限、託管服務、外部支援顧問參考答案收合
Allan Lo 顧問
務實的五件事
  1. 列一張表：公司有哪些網站、誰架的、放在哪家主機、聯絡人電話。一頁 Excel 就夠。
  2. 選對主機方案：優先使用會自動更新 PHP 的代管服務，並在合約中寫明更新責任。
  3. 套上 CDN／WAF：本案中 Cloudflare 連免費方案都自動加上防護規則，成本低、效果快。
  4. 能靜態就靜態：形象網站若無互動功能，可考慮改為靜態網站，大幅減少攻擊面。
  5. 知道去哪求助：TWCERT/CC、所屬產業 ISAC、地方政府資安輔導資源。
💡 顧問一句話：中小企業不需要做到滿分，但一定要做到「出事時知道打給誰、關得掉、修得了」。
